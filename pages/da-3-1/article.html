SELECT и порядок выполнения запроса

Запрос на SQL пишут, начиная с SELECT, а база выполняет его, начиная с FROM. После страницы вы сможете отбирать, сортировать и ограничивать строки учебной базы магазина, предсказывать, сколько строк останется после каждого шага, и объяснять, почему псевдоним из SELECT нельзя использовать в WHERE, но можно в ORDER BY.

01Идея: пишут с SELECT, выполняют с FROM

SQL — язык, на котором у базы данных просят таблицу: в запросе описывают, какой нужен результат, а как его получить, решает СУБД. Запрос состоит из предложений SELECT, FROM, WHERE и других; пишут их в одном порядке, а выполняются они в другом, логическом: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. Каждое предложение получает таблицу от предыдущего и передаёт следующему новую, обычно меньшую. Поэтому имя, которое столбец получил в SELECT, в WHERE и HAVING ещё не существует, а в ORDER BY уже есть.

Листайте шаги кнопками или стрелками ← → на клавиатуре. Ниже — та же мысль подробно.

Семь шагов по порядку

Этот порядок описан в документации PostgreSQL к команде SELECT1, а у Microsoft он прямо называется логическим порядком обработки2. Обязательно в запросе только SELECT, а FROM есть почти всегда. Остальные предложения можно пропускать, но в записи они стоят строго в том порядке, что и в начале сцены.

Имя появляется в SELECT

SUM(amount) — агрегатная функция: она сворачивает значения группы в одно число. AS revenue даёт результату имя, псевдоним. Он возникает на пятом шаге, поэтому WHERE и HAVING о нём не знают, а ORDER BY знает. Документация PostgreSQL говорит прямо: имя выходного столбца можно использовать в ORDER BY и GROUP BY, но не в WHERE и HAVING, там выражение пишут целиком1.

Порядок логический: он задаёт смысл запроса, а не то, в какой последовательности база на самом деле читает данные. Об этом — в разделе «Ограничения».

02Задача: почему revenue не находится

Учебная база shop — интернет-магазин товаров для дома за январь–март 2026: клиенты, товары, заказы и их позиции. Данные сгенерированы для учебника. На этой странице нужны две таблицы: orders, 231 заказ с суммой, статусом, брендом, каналом, оценкой и промокодом, и products, 32 товара.

Задача — читать и писать запросы к ним и понимать, почему похожий запрос то работает, то падает. Аналитик считает выручку брендов, называет её revenue и пишет WHERE revenue > 250000. PostgreSQL отвечает ошибкой column "revenue" does not exist, хотя имя объявлено строкой выше. А ORDER BY revenue в том же запросе работает.

Ниже сначала разобраны отдельные предложения: фильтры, сортировка, DISTINCT и LIMIT. Затем в интерактиве условие переезжает между WHERE и HAVING, и видно, что меняется.

03Фильтр, сортировка, первые строки

WHERE оставляет строки, для которых условие истинно. Условие — предикат: выражение, которое для каждой строки даёт «да», «нет» или, если в нём участвует пустое значение, «неизвестно». Это та же маска, что в pandas, только записанная словами. Строковые значения в SQL берут в одинарные кавычки: 'paid'. Двойные кавычки — для имён столбцов и таблиц.

Сортировка и место NULL

ORDER BY сортирует по одному или нескольким столбцам: ASC — по возрастанию, это вариант по умолчанию, DESC — по убыванию. Второй столбец решает, когда в первом значения равны. NULL — отметка «значения нет», и у сортировки для него своё правило. PostgreSQL считает NULL больше любого значения: при DESC такие строки идут первыми, при ASC — последними3. Место задают явно: NULLS FIRST или NULLS LAST. У 127 заказов из 231 нет оценки, и «три лучших по оценке» без NULLS LAST окажутся тремя заказами без оценки, это запрос 4 в разделе «Код».

DISTINCT

SELECT DISTINCT убирает из результата повторяющиеся строки. Он выполняется сразу после SELECT и сравнивает строку целиком: SELECT DISTINCT channel даёт три канала, а SELECT DISTINCT channel, brand — все встретившиеся пары канала и бренда. Внутри агрегата DISTINCT считает разные значения: по COUNT(DISTINCT customer_id) видно, что заказы сделали 52 клиента.

LIMIT и OFFSET

LIMIT n оставляет первые n строк, OFFSET m перед этим пропускает m строк. Вместе они дают пагинацию, выдачу по страницам: LIMIT 20 OFFSET 40 — третья страница по 20 строк. LIMIT выполняется последним, и «первые» значит первые после ORDER BY. Без ORDER BY база вернёт непредсказуемое подмножество строк, о чём документация PostgreSQL предупреждает отдельно3.

04WHERE и HAVING: запрос по шагам

Главное различие двух фильтров — что они видят. WHERE работает до группировки и проверяет каждую строку. HAVING работает после и проверяет каждую группу целиком, поэтому в нём пишут агрегаты. Столбец, которого нет в GROUP BY, в HAVING можно упомянуть только внутри агрегата: в группе клиента пять заказов, и спросить «какой у группы status» нельзя.

С пустыми значениями агрегаты обходятся по-разному. COUNT(*) считает строки группы, а COUNT(rating) — только строки, где в rating не NULL: в orders 231 строка, а заказов с оценкой 104.

В интерактиве — учебная выборка из orders: 15 заказов четырёх клиентов, 101, 104, 106 и 143. В запросе она называется sample. Запрос ищет двух клиентов с наибольшей выручкой среди тех, у кого не меньше трёх оплаченных заказов. Сначала предскажите результат.

Три вывода. Уберите status = 'paid' совсем, и HAVING посчитает отменённые заказы: у клиента 106 их два, и он поднимется на второе место с 19 960 ₽. Перенесите это условие в HAVING, и PostgreSQL откажется выполнять запрос. COUNT(*) в WHERE и псевдоним revenue в WHERE или HAVING тоже дают ошибку: агрегатов на втором шаге ещё нет, а имени revenue нет до пятого.

Выборка взята запросом SELECT order_id, customer_id, amount, status FROM orders WHERE customer_id IN (101, 104, 106, 143). Интерактив считает на JavaScript; все 27 расстановок условий сверены с PostgreSQL 16 на каждом из семи этапов.

05Диалекты: различия в мелочах

Ядро SQL задано стандартом, но у каждой СУБД свой диалект — набор расширений и отличий. SELECT, WHERE, GROUP BY и ORDER BY везде пишутся одинаково, расходятся мелочи, и как раз они ломают перенесённые запросы. SQLite и DuckDB — встраиваемые СУБД: база лежит в одном файле и работает внутри вашей программы. MS SQL — сервер Microsoft, BigQuery — облачное хранилище Google. Столбцы PostgreSQL, SQLite и DuckDB проверены запуском в разделе «Код» и сверены с документацией SQLite4 и DuckDB5. MS SQL2 и BigQuery6 описаны только по документации. FETCH FIRST n ROWS ONLY — запись из стандарта SQL:2008, она делает то же, что LIMIT1.

06Нюансы: NULL, регистр, порядок страниц

Сравнение с NULL. Любое сравнение с NULL даёт не TRUE и не FALSE, а UNKNOWN — третье значение троичной логики7. WHERE пропускает только TRUE, поэтому promo_code <> 'ЗИМА10' находит 19 заказов, а не 209: 190 строк без промокода выпали. Условие = NULL не находит ничего, пустоту ищут через IS NULL. Пустая строка '' — не NULL, таких промокодов в базе 7. Подробнее о троичной логике — на странице 3.4.

LIKE и регистр. В PostgreSQL LIKE различает регистр: 'лампа%' не найдёт «Лампа настольная», для поиска без учёта регистра есть ILIKE8. SQLite не различает регистр только у латиницы: status LIKE 'PAID' находит 195 строк, а 'лампа%' — ноль, и lower() кириллицу там тоже не меняет4. В PostgreSQL и DuckDB работает lower(product_name) LIKE 'лампа%'.

Порядок и страницы. Без ORDER BY порядок строк не гарантирован даже после GROUP BY: в интерактиве группы идут по customer_id только для удобства. Если сортировать по неуникальному столбцу, строки с равными значениями могут меняться местами от запроса к запросу, и страницы через LIMIT и OFFSET начнут повторять одни строки и терять другие3. Последним ключом ставят уникальный столбец: ORDER BY rating DESC NULLS LAST, order_id.

07Ограничения: логический порядок — не план

Логический порядок объясняет, что запрос значит, но не то, как база его выполняет. Планировщик PostgreSQL выбирает план выполнения: может найти нужные строки по индексу, не читая таблицу целиком, или остановиться, как только набрал строки для LIMIT. Результат при этом тот же, что дал бы логический порядок. План показывает команда EXPLAIN9; планы и индексы разобраны в блоке «Дата инженерия», тема 03.
