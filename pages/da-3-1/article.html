SELECT и порядок выполнения запроса

Как найти два бренда с наибольшей выручкой и исключить из расчёта отменённые заказы? На этом примере вы разберёте запрос на SQL по шагам. Увидите, когда отбираются строки, когда подсчитываются суммы и почему в PostgreSQL можно сортировать по псевдониму revenue, хотя в WHERE это имя недоступно.

01В каком порядке разбирать запрос

Запрос на SQL описывает результат, который вы хотите получить. Как именно прочитать и обработать данные, решает СУБД — система управления базами данных. Запрос состоит из предложений. В записи первым идёт SELECT, но для разбора нашего запроса удобно начать с FROM. Затем идут WHERE, GROUP BY, HAVING, SELECT, ORDER BY и LIMIT. Это логический порядок обработки. Он помогает понять, к чему относится условие и какие столбцы доступны на каждом шаге.

Переключайте шаги кнопками или клавишами ← и →. Проследите, как из 231 заказа получаются две строки с выручкой брендов.

Семь шагов одного запроса

Такой разбор запроса приведён в документации PostgreSQL1 и SQL Server2. В нашем примере нужны все семь предложений. Простому запросу достаточно одного SELECT, например SELECT 2 + 2. Когда вы добавляете предложения, соблюдайте порядок их записи. Похожие операции в pandas приведены в таблице.

Где можно использовать имя из SELECT

SUM(amount) — агрегатная функция. Она складывает суммы заказов в каждой группе. Запись AS revenue задаёт имя столбца с результатом. В PostgreSQL по этому имени можно сортировать в ORDER BY. В WHERE и HAVING псевдоним результата использовать нельзя. Чтобы отобрать бренды по суммарной выручке, в HAVING повторяют выражение SUM(amount). У GROUP BY есть отдельное правило PostgreSQL: здесь можно сослаться на имя выходного столбца, если само выражение допускает группировку1.

СУБД может выполнить вычисления в другом порядке, если ответ останется верным. В разделе «Ограничения» разберём, как посмотреть выбранный ею план.

02Почему PostgreSQL не находит столбец revenue

В учебной базе shop собраны данные о работе магазина товаров для дома за январь–март 2026 года. В этом уроке понадобятся две таблицы. В orders 231 заказ. Для каждого указаны сумма, статус, бренд, канал, оценка и промокод. В products 32 товара.

Аналитик считает выручку каждого бренда и хочет оставить только бренды с выручкой больше 250 000 ₽. В SELECT он задаёт имя revenue, а ниже пишет WHERE revenue > 250000. PostgreSQL сообщает, что столбец revenue не существует. Почему то же имя можно использовать в ORDER BY revenue?

Чтобы ответить, сначала выберем отдельные строки, отсортируем их и ограничим размер результата. Затем проверим в интерактиве, какие условия можно перенести из WHERE в HAVING.

03Как отобрать и отсортировать строки

WHERE оставляет строки, для которых условие истинно. Такое условие называют предикатом. Например, при сравнении amount >= 5000 возможны три результата — TRUE, FALSE и UNKNOWN. Если сумма неизвестна, результат этого сравнения тоже неизвестен. В PostgreSQL текстовые значения заключают в одинарные кавычки, например 'paid'. Двойные кавычки служат для имён, например для имени столбца.

Где при сортировке окажутся заказы без оценки

ORDER BY задаёт порядок строк. Для сортировки по возрастанию используют ASC (по умолчанию), по убыванию — DESC. Если значения первого столбца равны, их порядок определяет следующий ключ сортировки. У 127 заказов из 231 оценка отсутствует, и в столбце rating стоит NULL. В PostgreSQL при DESC строки с NULL по умолчанию идут первыми, при ASC — последними3. Поэтому запрос к этим заказам с ORDER BY rating DESC LIMIT 3 вернёт три заказа без оценки. Чтобы первыми шли заказы с высокой оценкой, укажите DESC NULLS LAST. В запросе 4 сравните оба варианта для первой недели февраля.

DISTINCT

SELECT DISTINCT удаляет повторы после выбора столбцов. При сравнении учитываются все выбранные значения. Например, SELECT DISTINCT channel вернёт три канала, а SELECT DISTINCT channel, brand — все пары канала и бренда, которые встречаются в заказах. Для подсчёта разных клиентов подходит COUNT(DISTINCT customer_id). В нашей таблице заказы сделали 52 клиента.

Как разбить результат на страницы

LIMIT n возвращает не больше n строк. Если указать OFFSET m, запрос сначала пропустит m строк. Так можно организовать пагинацию — показывать результат по страницам. Например, LIMIT 20 OFFSET 40 вернёт третью страницу, если на каждой помещается 20 строк. Чтобы однозначно определить состав страницы, нужен ORDER BY с ключами, которые задают порядок всех строк. Без сортировки состав первых 20 строк не гарантирован3.

04Когда использовать WHERE, а когда HAVING

WHERE проверяет отдельные строки до группировки. HAVING проверяет уже сформированные группы. Например, WHERE status = 'paid' оставляет только оплаченные заказы, а HAVING COUNT(*) >= 3 оставляет клиентов, у которых после отбора набралось хотя бы три заказа. Если группировать по customer_id, у одного клиента могут быть заказы с разными статусами. Его группу нельзя проверить по условию HAVING status = 'paid' в PostgreSQL.

COUNT(*) считает все строки, а COUNT(rating) — строки с указанной оценкой. Если применить обе функции ко всей таблице orders, получится 231 заказ, из них 104 с оценкой.

В интерактиве используется выборка sample. В ней 15 заказов четырёх клиентов с номерами 101, 104, 106 и 143. Начальная версия запроса выбирает двух клиентов, у которых больше всего выручки от оплаченных заказов. В сравнении участвуют клиенты с тремя или более такими заказами. Сначала попробуйте предсказать результат.

Уберите status = 'paid'. Теперь в количестве и сумме заказов учтены также отменённые. У клиента 106 два таких заказа. Сумма всех четырёх его заказов составит 19 960 ₽, и он окажется на втором месте. Если поместить условие по статусу в HAVING, PostgreSQL выдаст ошибку. Условие с COUNT(*) недопустимо в WHERE, а псевдоним revenue в этом запросе недоступен ни в WHERE, ни в HAVING.

Выборку можно получить запросом SELECT order_id, customer_id, amount, status FROM orders WHERE customer_id IN (101, 104, 106, 143) ORDER BY order_id. В интерактиве результат рассчитывает JavaScript. Для всех 27 сочетаний настроек результаты и ошибки сверены с PostgreSQL 16.

05Чем различаются диалекты SQL

Конкретная СУБД поддерживает свой диалект SQL. Например, один и тот же запрос с сортировкой по оценке может по-разному расположить строки без оценки. Ниже сравниваются PostgreSQL, встраиваемые СУБД SQLite и DuckDB, Microsoft SQL Server и облачная платформа BigQuery. Примеры для первых трёх систем проверены на учебной базе. Правила SQLite4 и DuckDB5, а также сведения о SQL Server2 и BigQuery6 приведены в документации. В PostgreSQL стандартная запись FETCH FIRST n ROWS ONLY ограничивает число строк так же, как LIMIT n1.

06NULL, регистр букв и порядок строк

Как найти заказы без промокода. При обычном сравнении с NULL, например promo_code <> 'ЗИМА10', результат неизвестен. В трёхзначной логике его обозначают UNKNOWN7. WHERE оставляет только строки с результатом TRUE. Из 231 заказа у 190 промокод равен NULL, у 22 указан «ЗИМА10», у 12 — «ВЕСНА15», у семи записана пустая строка. Поэтому условию promo_code <> 'ЗИМА10' соответствуют 19 заказов. Заказы без значения ищут с помощью IS NULL. Пустая строка '' под это условие не подходит. Подробнее о NULL — в уроке 3.4.

Как учесть регистр букв. В нашем примере PostgreSQL различает регистр в LIKE, поэтому шаблон 'лампа%' не подходит для названия «Лампа настольная». Для поиска без учёта регистра можно использовать ILIKE8. В стандартной сборке SQLite LIKE по умолчанию не различает регистр букв ASCII, а для кириллицы регистр важен. Выражение status LIKE 'PAID' находит 195 строк, а product_name LIKE 'лампа%' — ни одной. Встроенная в SQLite функция lower() также не меняет регистр кириллицы4. В PostgreSQL функция lower() учитывает языковые настройки базы. Если они поддерживают смену регистра кириллицы, как в учебной базе, выражение lower(product_name) LIKE 'лампа%' находит четыре товара. В DuckDB результат тот же. В PostgreSQL с настройкой C заглавная «Л» останется заглавной, и запрос вернёт ноль строк.

Как избежать повторов на соседних страницах. В интерактиве группы расположены по номерам клиентов, чтобы их было легче сравнить. SQL гарантирует порядок только при ORDER BY. Даже с сортировкой по оценке у разных заказов могут оказаться одинаковые оценки. Тогда на соседних страницах один заказ может появиться дважды, а другой не попасть ни на одну из них3. Для неизменившегося набора заказов порядок станет однозначным, если последним ключом добавить уникальный номер заказа: ORDER BY rating DESC NULLS LAST, order_id.

07Как СУБД выбирает план выполнения

Планировщик PostgreSQL выбирает план выполнения запроса. Например, если есть подходящий индекс, СУБД может найти заказы по индексу, а с LIMIT иногда может завершить поиск, когда нужные строки уже найдены. Логический разбор помогает проверить смысл запроса. Выбранный план можно посмотреть с помощью EXPLAIN9. Планы и индексы подробнее разбираются в теме 03 блока «Дата инженерия».
