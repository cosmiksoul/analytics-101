Загрузка из файлов, баз и API

Данные для анализа редко лежат в одном месте: часть приходит файлом, часть живёт в базе, часть отдаёт чужой сервис. После этой страницы вы сможете загрузить в DataFrame CSV, Excel, результат запроса и ответ API с явными типами и будете знать, где по дороге данные портятся без единой ошибки.

01Идея: у каждого источника своя труба и свой фильтр

Каждый источник подключается к DataFrame своей трубой: файл читает read_csv или read_excel, базу — read_sql с запросом, API — цикл запросов через библиотеку requests. На каждой трубе стоит фильтр, и данные проходят его целыми, только если вы знаете его правила: у файла это кодировка и запись чисел и дат, у базы — параметры запроса, у API — страницы и лимит запросов. Самые опасные поломки тихие: pandas не падает, а оставляет сумму строкой или меняет день с месяцем. Поэтому формат и типы задают явно, а результат проверяют сразу после загрузки.

Листайте шаги кнопками или стрелками ← → на клавиатуре. Ниже — та же мысль подробно.

CSV: текст с договорённостями

CSV — текстовая таблица: строка файла — запись, значения разделены особым символом. Ни кодировку, ни разделитель, ни запись чисел и дат формат в файле не хранит. Это договорённости, которые читающий знает заранее, и главные аргументы read_csv описывают именно их1217:

  • encoding — кодировка. По умолчанию UTF-8, а старые системы часто пишут в cp1251 (страница 1.4).
  • sep — разделитель полей. По умолчанию запятая; в русских выгрузках чаще «;», потому что запятая занята дробями.
  • quotechar — символ кавычек: разделитель внутри кавычек — часть текста. По умолчанию двойная кавычка.
  • decimal и thousands — десятичный разделитель и разделитель тысяч; по умолчанию точка и «нет».
  • dtype — словарь «столбец → тип данных»; без него тип угадывается.
  • parse_dates и date_format — какие столбцы сделать датами и по какому формату.
  • usecols — какие столбцы читать.

Без dtype pandas пробует целые числа, потом дробные, потом логические значения, а всё остальное оставляет текстом — в pandas 3 это тип str, а не object, как раньше3. Даты без parse_dates тоже остаются текстом.

Excel: книга из нескольких листов

Excel хранит тип каждой ячейки, поэтому read_excel реже путает даты и числа. Зато листов в книге бывает несколько: sheet_name выбирает лист по имени или номеру, а sheet_name=None читает все сразу и возвращает словарь «имя листа → DataFrame»4. Для .xlsx нужна библиотека openpyxl.

База: запрос с параметрами

До базы pandas добирается через SQLAlchemy — библиотеку для PostgreSQL, MySQL, SQLite и других баз. Подключение описывает строка подключения: тип базы, драйвер, учётная запись, адрес и имя базы, например postgresql+psycopg://user:***@host:5432/shop7. По ней create_engine создаёт движок — объект, который открывает соединения, — а read_sql отправляет через него запрос и складывает ответ в DataFrame5.

Значения, которые меняются от запуска к запуску, в текст запроса не вклеивают. В параметризованном запросе на их месте стоят метки :start и :end, а значения передают отдельно, словарём params. Драйвер сам передаёт или экранирует значения, и значение не становится частью кода SQL68.

Если собрать запрос f-строкой, значение становится кодом. Строка 2026-04-01' OR '1'='1 закрывает кавычку и дописывает условие, которое верно всегда, — это SQL-инъекция. В анимации такой запрос вернул все 15 заказов вместо 12, вместе с декабрьскими; в параметре тот же текст — просто странное значение8.

Типы из базы тоже проверяют: SQLite хранит даты текстом, и без parse_dates столбец date приходит строками. dtype у read_sql работает так же, как у read_csv5.

API: страницы, лимиты, повторы

API отвечает на HTTP-запросы — обращения к серверу по адресу: клиент просит адрес вроде /v1/orders?page=1, сервер возвращает код ответа и тело, обычно в формате JSON. 200 — «всё в порядке», 401 — «неверный ключ», 404 — «нет адреса», 429 — «слишком часто», 5xx — «сбой на сервере». В requests запрос — одна строка: адрес, params, заголовки headers и таймаут, то есть сколько секунд ждать ответа9.

Заголовки — служебные поля запроса; в Authorization передают ключ доступа. Сам ключ берут из переменной окружения, а не пишут в коде.

Большой ответ сервер отдаёт частями — это пагинация. Клиент просит страницу 1, получает 4 записи и номер следующей next_page, просит её — и так, пока next_page не придёт пустым: null в JSON, None в Python. Признак конца описывает документация: здесь это пустой next_page, у других API — пустой список записей или нет ссылки на следующую страницу.

Учебный сервер пропускает 30 запросов в минуту — не чаще раза в 2 секунды. Если спешить, он отвечает кодом 429 Too Many Requests10 и заголовком Retry-After — сколько секунд ждать11. Вежливый клиент сам делает паузу между запросами, а на 429 и 5xx ждёт и повторяет запрос. Если сервер не подсказал срок, паузу удваивают с каждой попыткой — это экспоненциальная задержка.

Записи из API приходят вложенными: {"brand": {"name": "Бриз"}, "total": {"amount": 6348.6}}. Функция json_normalize раскладывает их в плоскую таблицу со столбцами brand.name и total.amount12, дальше остаётся переименовать столбцы.

parquet: сохранить вместе с типами

Собранную таблицу сохраняют, чтобы не собирать её заново. CSV для этого плох: даты и типы в нём снова станут текстом. Parquet хранит значения по столбцам вместе со схемой — именами и типами13, поэтому после to_parquet и read_parquet таблица возвращается той же; в pandas эту работу делает pyarrow14.

03Как read_csv разбирает файл

read_csv работает в несколько шагов, у каждого свои аргументы. Сначала байты становятся текстом по encoding. Потом текст режется на строки и поля: поле кончается на разделителе sep, если тот не стоит внутри кавычек quotechar. Первая строка становится именами столбцов.

Дальше pandas сверяет число полей. Если в строке полей больше, чем имён в заголовке, read_csv останавливается с ошибкой ParserError. Исключение — первая строка данных: если в ней ровно на одно поле больше, pandas решит, что первое поле — неявный индекс, и молча сдвинет столбцы.

Потом столбцы получают типы: числа читаются с учётом decimal и thousands, столбцы из dtype приводятся к заданному типу, из parse_dates — к датам. Если date_format не задан, формат дат pandas угадывает по первому значению столбца1. Для 04.01.2026 догадка — «месяц.день.год», и 4 января становится 1 апреля без единого предупреждения.

04Нюансы: явные типы, большие файлы, секреты и даты

Типы задают явно, а не угадывают. Догадка зависит от содержимого: на этой неделе в amount одни целые суммы, и он int64, на следующей придёт 1569,80, и без decimal="," столбец тихо станет str. Словарь dtype делает ошибку громкой: с dtype={"amount": "float64"} без decimal чтение файла CRM падает с ValueError: could not convert string to float: '1569,80'. Громкую ошибку видно сразу, а не в отчёте.

Большой файл читают по кускам. С chunksize функция read_csv возвращает не таблицу, а итератор кусков: каждый шаг цикла даёт следующие chunksize строк2. Так считают суммы по файлу, который не помещается в память: кусок обработали, результат сохранили, кусок выбросили. На учебном файле chunksize=3 даёт куски по 3, 3 и 2 строки.

Секреты — не в коде. Пароль от базы и ключ API в тексте скрипта рано или поздно попадут в Git или в чат. Их держат в переменных окружения и читают через os.environ["SHOP_API_TOKEN"]15, а файл .env с ними вносят в .gitignore. Ключ передают в заголовке, а не в адресе: адреса с параметрами оседают в журналах серверов.

Даты остаются строками без parse_dates. Сам read_csv текст в даты не превращает: без parse_dates столбец date — str, и сортировка по нему идёт по символам: 2 марта встаёт раньше 4 января. parse_dates без формата спасает не всегда: если формат угадан по первой строке как «месяц.день.год», а ниже встретится 14.01.2026, весь столбец молча останется строками. Надёжно — parse_dates вместе с date_format.

06Код: три трубы и один файл

Каждый источник — функция в своём модуле, сборка их импортирует; данные те же, что в анимации. Первый модуль читает файл CRM с явными типами и показывает две тихие ошибки.

Запрос к базе. Чтобы пример запускался без сервера, параметризованный запрос через SQLAlchemy выполнен на SQLite с такой же таблицей orders; строка подключения к PostgreSQL — в комментарии. Последние строки повторяют инъекцию из анимации.

Обход API. Внешней сети в песочнице нет, поэтому рядом запущен учебный сервер на http.server16: 10 заказов по 4 на страницу, проверка ключа, не больше 30 запросов в минуту. Ключ учебный, из переменной окружения. Последняя строка нарочно делает два запроса подряд, чтобы показать повтор после 429.

Сборка: склейка трёх кусков через pd.concat и сохранение; для сравнения таблица записана и в CSV.
