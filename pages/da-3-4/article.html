Подзапросы, CTE, NULL и типы

Длинный запрос легче читать и проверять, если разложить его на шаги с именами. После страницы вы сможете писать подзапросы и CTE, находить строки, потерянные из-за NULL, и сравнивать даты, строки и числа без сюрпризов от типов.

01Идея: шаги с именами и третье значение UNKNOWN

Запрос из вложенных подзапросов выполняется изнутри наружу, и промежуточный результат в нём не увидеть. Конструкция WITH даёт каждому шагу имя и выстраивает шаги сверху вниз, а любой из них можно запустить отдельно, как таблицу, и найти, где пропали строки. Чаще всего строки теряются из-за NULL: сравнение с ним даёт не TRUE и не FALSE, а третье значение UNKNOWN. WHERE пропускает только TRUE, поэтому условие promo_code <> 'ЗИМА10' вместе с акционными заказами молча выбрасывает все заказы без промокода.

Листайте шаги кнопками или стрелками ← → на клавиатуре. Числа в сцене — настоящий вывод PostgreSQL 16 на учебной базе магазина.

Подзапрос в WHERE, FROM и SELECT

Подзапрос — это SELECT в скобках внутри другого запроса. Что он должен вернуть, зависит от места, где он стоит1.

ГдеЧто вернутьПример на учебной базе
WHEREодно значение или список для INamount > (SELECT AVG(amount) FROM orders WHERE status = 'paid'): 75 из 195 оплаченных заказов дороже среднего чека 4 677 ₽
FROMтаблицу — производнуюзапрос из сцены: (SELECT * FROM orders WHERE status = 'paid') AS paid

Подзапрос в SELECT и в сравнении внутри WHERE — скалярный: одна строка и один столбец. Если строк ноль, подставляется NULL, если больше одной, запрос падает с ошибкой «more than one row returned by a subquery used as an expression»2. Производной таблице по стандарту нужно имя после AS, хотя PostgreSQL 16 разрешает его опустить1.

Коррелированный подзапрос и EXISTS

Подзапросы выше не зависят от внешнего запроса и считаются один раз. Коррелированный ссылается на столбец внешней строки и логически выполняется заново для каждой из них. Так находят заказы дороже среднего чека своего же клиента: WHERE o.amount > (SELECT AVG(o2.amount) FROM orders o2 WHERE o2.customer_id = o.customer_id AND o2.status = 'paid'). Среди оплаченных таких 81.

EXISTS (подзапрос) — предикат, то есть условие, которое отвечает TRUE, FALSE или UNKNOWN. EXISTS даёт TRUE, если подзапрос вернул хотя бы одну строку, и FALSE, если ни одной3. Что стоит в SELECT подзапроса, неважно, поэтому пишут SELECT 1. Обычно EXISTS коррелирован: EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id AND o.promo_code = 'ЗИМА10') находит 15 клиентов, которые хоть раз вводили код ЗИМА10. UNKNOWN у EXISTS не бывает, поэтому NOT EXISTS — надёжное анти-соединение из 3.2.

CTE: у каждого шага имя

Обобщённое табличное выражение (common table expression, CTE) записывается как WITH имя AS (запрос). Документация PostgreSQL описывает его как временную таблицу, которая существует только в одном запросе4. Шагов через запятую может быть сколько угодно, и каждый видит предыдущие по имени.

Результат тот же, что у вложенных подзапросов, меняется форма. Шаги идут сверху вниз в порядке выполнения, у каждого смысловое имя, на шаг можно сослаться дважды без копирования текста. Для отладки главное другое: финальный SELECT можно заменить на SELECT COUNT(*) FROM шаг и увидеть, где число строк разошлось с ожиданием. Маркус Винанд называет такой стиль грамотным SQL (literate SQL)5.

02Задача: отчёт, который сходится с итогом

Аналитик собирает отчёт по учебной базе: выручка, число заказов и средняя оценка по каналам и по неделям квартала, отдельно — без зимней акции. В заказах есть всё, что ломает такие отчёты. Промокод бывает NULL, пустой строкой или кодом, у 91 оплаченного заказа нет оценки, время заказа хранится меткой времени, и один заказ сделан ровно в полночь.

Задача страницы — писать многошаговые запросы, которые можно читать и проверять по шагам, и не терять строки из-за NULL и типов. Проверка простая: сумма по сегментам совпадает с общим итогом, а число строк на каждом шаге — с ожиданием. Такие отчёты подробно разбирает Кэти Танимура6.

03Троичная логика: TRUE, FALSE и UNKNOWN

NULL — отметка «значения нет или оно неизвестно», а не значение. Поэтому сравнение с NULL не бывает ни истинным, ни ложным, и SQL отвечает третьим значением UNKNOWN. Это касается и NULL = NULL: два неизвестных значения не обязаны совпадать7. Так устроена троичная логика (three-valued logic).

WHERE, ON и HAVING пропускают строку, только если условие дало TRUE: UNKNOWN отбрасывается так же, как FALSE7. Логические операторы считают по таблицам истинности8. AND даёт FALSE, если хоть одна часть FALSE, OR даёт TRUE, если хоть одна часть TRUE. В остальных случаях UNKNOWN в любой части даёт UNKNOWN, и NOT UNKNOWN — тоже UNKNOWN.

x IN (a, b) раскрывается в x = a OR x = b, а x NOT IN (a, b) — в x <> a AND x <> b. Если в списке есть NULL, одно из неравенств всегда UNKNOWN, и NOT IN не бывает TRUE3. Спросить про NULL можно только предикатами IS NULL и IS NOT NULL: они отвечают TRUE или FALSE9.

В интерактиве шесть оплаченных заказов учебной базы, выбранных запросом SELECT order_id, rating, promo_code FROM orders WHERE order_id IN (1001, 1004, 1008, 1011, 1016, 1083). Расчёт идёт на JavaScript, а каждое условие сверено с PostgreSQL на всех 24 сочетаниях значений rating и promo_code. Сначала предскажите.

COALESCE и NULLIF

COALESCE(x, y, …) возвращает первый аргумент, который не NULL10. Он подставляет значение до сравнения, и условие перестаёт давать UNKNOWN: так в сцене вернулись 159 заказов. NULLIF(a, b) делает обратное и возвращает NULL, если a = b, иначе a. Им превращают «пустышку» вроде пустой строки в настоящий NULL и защищают деление: revenue / NULLIF(n, 0) вернёт NULL вместо ошибки деления на ноль.

04Типы: даты, строки, числа

У каждого столбца есть тип: integer, numeric, text, date, timestamp (метка времени), boolean. Значение в кавычках вроде '2026-02-12' — литерал без заданного типа: PostgreSQL приводит его к типу столбца, с которым сравнивает11. Явное приведение типов записывают как CAST(x AS тип) или короче, как принято в PostgreSQL: x::тип2.

Для дат есть две главные функции12. DATE_TRUNC('week', ts) обрезает метку до начала недели — понедельника, 00:00:00. С 'month' получится первое число месяца, с 'day' — полночь. EXTRACT(поле FROM ts) достаёт число: hour — час, isodow — день недели от 1 (понедельник) до 7, week — номер недели по ISO 8601. Для заказа 1004 от 2 января 2026 года, 23:37, это 2025-12-29 00:00:00, 23, 5 и 1. EXTRACT в PostgreSQL возвращает numeric.

Строковые функции LOWER, TRIM, LENGTH, SUBSTRING пропускают NULL насквозь: LENGTH('') — 0, а LENGTH(NULL) — NULL. Пустая строка — значение, NULL — его отсутствие, и в учебной базе есть оба.

DATE_TRUNC есть в PostgreSQL и DuckDB, а в SQLite его нет. В SQLite нет и отдельного типа для дат: они хранятся строками13. Неделю там считают функцией date с модификаторами, а метку времени сравнивают с литералом как текст. Оба отличия показаны запуском в разделе «Код».

05Нюансы: NOT IN, полночь, материализация, пустые строки

NOT IN с NULL в подзапросе возвращает пусто. Ищем клиентов, которые никого не пригласили. NOT IN по referrer_id даёт 0: у 44 клиентов referrer_id — NULL, и неравенство с ним всегда UNKNOWN. NOT EXISTS находит 453. Подзапрос в NOT IN фильтруют условием IS NOT NULL или заменяют на NOT EXISTS14.

Дата против метки времени. created_at = '2026-02-12' сравнивает с 2026-02-12 00:00:00 и находит один заказ из пяти — 1008, сделанный ровно в полночь. Проверка на таком дне выглядит успешной, и ошибку легко пропустить. BETWEEN с '2026-02-28' по той же причине теряет три заказа 28 февраля после полуночи. Надёжная форма — полуинтервал: created_at >= '2026-02-01' AND created_at < '2026-03-01'.

CTE не всегда материализуется. Материализация — расчёт шага отдельно, с сохранением результата на время запроса. До PostgreSQL 12 так считалась любая CTE15. Теперь шаг без побочных эффектов, на который ссылаются один раз, встраивается в основной запрос, а шаг с двумя ссылками считается один раз и сохраняется4. Слова MATERIALIZED и NOT MATERIALIZED меняют это решение. В плане запроса ниже встроенная CTE исчезла: остался один проход по orders с обоими фильтрами. С MATERIALIZED появились отдельный шаг «CTE paid» и чтение из него — CTE Scan.

NULLIF для пустой строки. COUNT(promo_code) по оплаченным заказам даёт 36: пять пустых строк — тоже значения. COUNT(NULLIF(promo_code, '')) даёт 31 — столько раз ввели настоящий код.

06Ограничения: рекурсия, процедуры, скорость

Страница не касается рекурсивных CTE (WITH RECURSIVE), которыми обходят иерархии вроде цепочки приглашений по referrer_id, и процедурного SQL — функций, циклов и переменных внутри базы. Это тема ДЕ 04. Как база выбирает план и когда помогают индексы, разобрано в ДЕ 03, здесь EXPLAIN нужен только для того, чтобы увидеть, встроилась ли CTE.

Интерактив моделирует правила на шести строках, а не исполняет SQL. Примеры проверены в PostgreSQL 16, SQLite и DuckDB, а MS SQL и BigQuery здесь не показаны.

07Код: отчёт из CTE, потерянные строки, недели

Блоки идут по задаче на той же учебной базе. Первый — отчёт из сцены, уже исправленный, и приём отладки: тот же WITH, но в конце размер каждого шага.

Второй ищет строки, потерянные из-за NULL: группирует по промокоду и значению условия, находит выпавшие строки анти-соединением и сравнивает расчёты по rating с NULL и без них.

COALESCE — не всегда лекарство. AVG(COALESCE(rating, 0)) считает отсутствие оценки нулём, и средняя падает с 4,03 до 2,15. Третий блок — недельный отчёт через DATE_TRUNC с полуинтервалом по датам.
