Подзапросы, CTE, NULL и типы

Из 195 оплаченных заказов магазин хочет исключить 20 заказов по зимней акции. Почему запрос оставил всего 16? Вы разберёте его на подзапросы, дадите промежуточным результатам имена с помощью CTE и увидите, как NULL в поле промокода влияет на выручку в отчёте.

01На каком шаге из отчёта исчезли заказы

Вложенные запросы бывает трудно проверять: сначала нужно понять, какие строки возвращает внутренний запрос и как их использует внешний. С помощью WITH можно дать каждому промежуточному результату имя и проверить число строк в нём. Так найдём ошибку в фильтре promo_code <> 'ЗИМА10'. Если в поле промокода стоит NULL, сравнение даёт UNKNOWN. Условие WHERE оставляет только строки, для которых получено TRUE. Из отчёта исчезают и заказы по акции, и заказы с неизвестным промокодом.

Переключайте шаги кнопками под анимацией или клавишами ← и →. В анимации показаны результаты запросов к учебной базе магазина в PostgreSQL 16.

Подзапрос в WHERE, FROM и SELECT

Подзапрос — запрос внутри другого запроса. В нашем примере это SELECT в скобках. В зависимости от контекста его результат можно использовать как таблицу, набор значений или отдельное значение1.

Скалярный подзапрос нужен там, где ожидается одно значение, например справа от знака >. В PostgreSQL он должен вернуть один столбец и не больше одной строки. Если строк нет, результатом будет NULL. Если строк несколько, база выдаст ошибку2. У подзапроса в FROM свой результат из строк и столбцов. Ему удобно дать имя, например AS paid. В PostgreSQL 16 это имя можно опустить1.

Коррелированный подзапрос и EXISTS

В примере со средним чеком внутренний запрос использует всю выборку оплаченных заказов. У коррелированного подзапроса результат зависит от значения во внешней строке. Например, условие o.amount > (SELECT AVG(o2.amount) FROM orders o2 WHERE o2.customer_id = o.customer_id AND o2.status = 'paid') сравнивает сумму заказа со средним чеком того же клиента. Так найдётся 81 оплаченный заказ. Как именно выполнить сравнение, решает оптимизатор.

EXISTS проверяет, вернул ли подзапрос хотя бы одну строку. У этого предиката два результата: TRUE, если строка есть, и FALSE, если строк нет3. Например, EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id AND o.promo_code = 'ЗИМА10') находит 15 клиентов, у которых есть заказ с зимним промокодом. Здесь важно само совпадение, поэтому в подзапросе достаточно SELECT 1. Если нужны клиенты без совпадений, используйте NOT EXISTS. Этот приём называется антисоединением.

Как дать промежуточному результату имя с помощью WITH

Обобщённое табличное выражение (common table expression, CTE) записывают как WITH имя AS (запрос). Этим именем можно пользоваться в пределах одной SQL-команды4. Если шагов несколько, перечислите их через запятую. В обычной цепочке следующий шаг может сослаться на результат предыдущего.

Перепишем вложенные запросы через WITH, сохранив тот же расчёт. Теперь, чтобы проверить конкретный шаг, достаточно заменить итоговый SELECT, например на SELECT COUNT(*) FROM paid, и выполнить весь запрос вместе с WITH. Порядок записи помогает проследить зависимости. Физический порядок операций показывает план запроса. У Маркуса Винанда есть другие примеры того, как имена промежуточных результатов помогают читать SQL5.

02Как проверить отчёт по заказам

Магазину нужен квартальный отчёт по каналам и неделям: выручка, число заказов и средняя оценка. Отдельно посчитаем показатели без зимней акции. В выгрузке встречаются три разных случая: записан промокод, записана пустая строка или стоит NULL. У 91 оплаченного заказа нет оценки. Время создания известно вплоть до секунды, и один из примеров приходится ровно на полночь.

Сверим число заказов до и после каждого фильтра, а затем сложим выручку всех каналов и сравним её с общей выручкой той же выборки. Другие примеры проверки пропусков и построения отчётов по времени есть у Кэти Танимуры6.

03Когда условие даёт UNKNOWN

NULL означает, что значение отсутствует или неизвестно. При обычном сравнении с ним через =, <> или > результат тоже неизвестен. Даже NULL = NULL даёт UNKNOWN7. Наряду с TRUE и FALSE это третье возможное значение условия в трёхзначной логике SQL.

Условие WHERE оставляет строки с TRUE, а HAVING по тому же правилу отбирает группы. В JOIN условие ON определяет, какие пары строк совпали: для совпадения нужен TRUE. При внешнем соединении строка без совпадения всё же может попасть в результат7. Для AND достаточно одного FALSE, чтобы всё условие стало ложным. Для OR достаточно одного TRUE, чтобы оно стало истинным. Если эти правила не дают ответа, а значение одной части неизвестно, результат тоже будет UNKNOWN. Например, TRUE AND UNKNOWN и NOT UNKNOWN дают UNKNOWN8.

Выражение x IN (a, b) соответствует x = a OR x = b, а x NOT IN (a, b) — x <> a AND x <> b. Если в списке есть NULL, одно из сравнений даёт UNKNOWN. В этом случае NOT IN даст FALSE при найденном совпадении и UNKNOWN в остальных случаях. Ни одна строка не пройдёт через такой фильтр3. Для проверки самого пропуска используйте IS NULL или IS NOT NULL. Они всегда возвращают TRUE или FALSE9.

В интерактиве шесть оплаченных заказов. Для каждого можно изменить оценку и промокод и увидеть, пройдёт ли строка через WHERE. В исходной выборке это заказы № 1001, 1004, 1008, 1011, 1016 и 1083. Перед запуском попробуйте ответить на вопрос.

COALESCE и NULLIF

COALESCE возвращает первый аргумент, значение которого известно10. Если все аргументы равны NULL, результат тоже NULL. В нашем отчёте COALESCE(promo_code, '') подставляет пустую строку перед сравнением с зимним промокодом. Благодаря этому в отчёт возвращаются 159 заказов. NULLIF(a, b) возвращает NULL, если аргументы равны, и значение a в остальных случаях. Например, NULLIF(promo_code, '') заменяет пустую строку на NULL, а revenue / NULLIF(n, 0) позволяет избежать деления на ноль.

04Что меняет тип столбца при сравнении

Сумма заказа может иметь тип integer или numeric, промокод — text, дата — date, а дата вместе со временем — timestamp. В PostgreSQL тип строкового литерала вроде '2026-02-12' без явного указания определяется по контексту. При сравнении со столбцом timestamp этот литерал обозначает полночь в начале дня11. Для явного приведения типа используйте CAST(x AS тип) или сокращённую запись PostgreSQL x::тип2.

Для отчёта по неделям нам пригодятся две функции PostgreSQL12. DATE_TRUNC возвращает начало периода. Для 'week' это понедельник в полночь. EXTRACT извлекает из даты или метки времени указанное поле. Например, заказ № 1004 сделан 2 января 2026 года в 23:37. Неделя началась 29 декабря 2025 года. Поля hour, isodow и week дают 23, 5 (пятница) и 1 (первая неделя по ISO).

Пустая строка и NULL дают разные результаты. Например, LENGTH('') возвращает 0, а LENGTH(NULL) — NULL. У функций LOWER, TRIM и SUBSTRING результат при отсутствующем строковом аргументе тоже будет NULL.

В PostgreSQL и DuckDB есть функция DATE_TRUNC. В SQLite дату начала недели можно получить функцией date с модификаторами. В SQLite нет отдельного типа для дат: их представляют текстом или числами13. В учебном файле метки времени хранятся как текст. Поэтому строка с одной датой и строка с той же датой и временем в полночь при сравнении на равенство различаются.

05Что проверить при поиске пропусков и выборе периода

Клиенты без приглашений. В столбце referrer_id у 44 клиентов стоит NULL. Поэтому фильтр NOT IN по этому столбцу не находит никого. С NOT EXISTS получаем 45 клиентов, которые никого не пригласили3. Для наших непустых идентификаторов клиента тот же результат даст NOT IN, если исключить NULL из подзапроса условием IS NOT NULL14.

Заказы за день. Условие created_at = '2026-02-12' находит заказ № 1008, оформленный ровно в полночь. Ещё четыре заказа за тот же день в результат не попадают. Похожая ошибка возникает при выборе февраля: правая граница '2026-02-28' в BETWEEN исключает три заказа, оформленных позже полуночи 28 февраля. Используйте полуинтервал от начала февраля до начала марта: created_at >= '2026-02-01' AND created_at < '2026-03-01'.

Когда PostgreSQL вычисляет CTE отдельно. Материализация означает, что промежуточный результат вычисляют отдельно и сохраняют для чтения в пределах команды. До PostgreSQL 12 выражения WITH такого вида не встраивались в основной запрос15. В PostgreSQL 16 нерекурсивный SELECT без побочных эффектов обычно встраивается при одной ссылке и материализуется при нескольких. Для такого выражения решение можно изменить с помощью MATERIALIZED или NOT MATERIALIZED4. В первом плане запроса ниже виден один проход по orders с обоими фильтрами. Во втором отдельный узел CTE Scan читает результат paid.

Пустые промокоды. Среди оплаченных заказов COUNT(promo_code) даёт 36. В это число входят пять пустых строк. Если заменить их на NULL с помощью COUNT(NULLIF(promo_code, '')), останется 31 заказ с непустым промокодом.

06Где ещё встречаются CTE и планы запросов

В уроке мы используем WITH для последовательных шагов одного отчёта. Для иерархических данных есть рекурсивные CTE. Например, по полю referrer_id можно восстановить цепочку приглашений. В курсе по инженерии данных эти задачи рассматриваются отдельно, как и выбор индексов по плану запроса.

Интерактив воспроизводит правила SQL на шести строках. Те же условия можно выполнить в PostgreSQL с помощью файла three_valued.sql из материалов урока.
