Агрегаты и группировка

У магазина 195 оплаченных заказов за квартал. В каком канале покупают чаще, а в каком больше средний чек? Чтобы сравнить сегменты, сгруппируем заказы по каналу и рассчитаем показатели внутри каждой группы. Затем добавим общий итог и проверим, почему он может отличаться от среднего по строкам отчёта.

01Как из заказов получается отчёт по брендам

Агрегатная функция вычисляет один результат по набору строк. Например, COUNT(*) считает заказы, SUM(amount) складывает их суммы, а AVG(amount) вычисляет средний чек. С помощью GROUP BY можно выполнить те же расчёты отдельно для каждого бренда. WHERE определяет, какие заказы войдут в расчёт, а HAVING — какие группы попадут в отчёт.

Переключайте шаги кнопками или стрелками ← и → на клавиатуре.

Как агрегаты учитывают пропуски

Рассмотрим пять функций: COUNT, SUM, AVG, MIN и MAX1. NULL обозначает отсутствие значения. COUNT(*) учитывает каждую строку, даже если оценка заказа неизвестна. COUNT(rating) учитывает только строки с оценкой2. Покупатели оценили 104 из 195 оплаченных заказов. Поэтому AVG(rating) делит сумму оценок на 104.

Если запрос без GROUP BY не отобрал ни одной строки, COUNT(*) вернёт 0, а SUM(amount) — NULL1. Для подсчёта покупателей пригодится COUNT(DISTINCT customer_id). Покупатель с пятью заказами войдёт в результат один раз.

Группировка по нескольким столбцам

В GROUP BY можно указать несколько столбцов. Тогда каждой группе соответствует сочетание значений, которое встретилось в данных. В учебной базе в каждом из трёх каналов есть оплаченные заказы всех четырёх брендов, поэтому получаем 12 групп. В анимации используется только brand. Для «Совы» в группе восемь заказов. Чтобы вывести по ним одну сумму, укажите, что именно нужно вычислить, например SUM(amount) или MAX(amount)3.

В уроке 2.4 ту же задачу решал groupby в pandas4. Если выполнить группировку в SQL, из базы можно получить уже готовую таблицу по сегментам.

HAVING — фильтр для групп

Логический порядок из урока 3.1 выглядит так: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. На этапе WHERE группы ещё не сформированы, поэтому WHERE COUNT(*) >= 4 вызовет ошибку. В HAVING можно проверять агрегат, даже если его нет среди столбцов результата3. Например, в группе «Кедр» три оплаченных заказа. Условие HAVING COUNT(*) >= 4 исключит этот бренд из отчёта.

Если условие относится к отдельному заказу, укажите его в WHERE. Например, фильтр по статусу сократит число строк ещё до группировки. В PostgreSQL выражение для проверки нужно записать в HAVING целиком. SQLite и DuckDB разрешают также сослаться на псевдоним агрегата, заданный в SELECT.

02Квартальный отчёт по каналам

Маркетологу нужна таблица по заказам магазина за квартал. Для каждого канала нужны число заказов и покупателей, доля отмен, выручка по месяцам и средний чек. В последней строке должны быть показатели магазина в целом.

Возьмём данные из учебной базы shop. Долю отмен будем считать по всем заказам, а выручку и средний чек — по оплаченным. Для каждой метрики выберем нужные строки и проверим знаменатель. Другие примеры отчётов по группам есть у Танимуры5 и Болье6.

03Несколько показателей в одном запросе

Чтобы рассчитать долю отмен, нужно знать, сколько заказов отменили и сколько их было всего. Эти числа удобно получить в одной строке отчёта. Условный агрегат позволяет отобрать строки для отдельного показателя, сохранив для остальных показателей все заказы группы.

Выражение CASE возвращает значение в зависимости от условия. Например, SUM(CASE WHEN status = 'cancelled' THEN 1 ELSE 0 END) присваивает отменённым заказам единицу, остальным — ноль и складывает результат. Без ELSE выражение CASE вернёт NULL для остальных заказов. Если отмен в группе не было, сумма таких значений тоже даст NULL.

SUM(CASE WHEN условие THEN 1 ELSE 0 END) = COUNT(*) FILTER (WHERE условие)Для непустой группы обе записи дают число строк, в которых выполнено условие. В канале «органика» оба выражения насчитают 15 отмен из 94 заказов.

Предложение FILTER передаёт агрегату только те строки, для которых условие в скобках истинно2. Такая запись есть в PostgreSQL, SQLite и DuckDB. Если СУБД её не поддерживает, условие можно выразить через CASE7. За каждый месяц посчитаем SUM(amount) FILTER (WHERE …) в своём столбце. Получится сводная таблица с каналами в строках и месяцами в столбцах, как при использовании pivot_table в pandas8.

04Как получить общий средний чек

Когда известны все суммы оплаченных заказов, средний чек легко посчитать: нужно разделить общую выручку на число этих заказов. А если в отчёте остались только средние чеки и число заказов по группам?

Среднее от средних даёт каждой группе одинаковый вес. Например, группа из четырёх заказов влияет на итог так же, как группа из восемнадцати. Чтобы учесть каждый заказ с одинаковым весом, вычислите взвешенное среднее. Умножьте средний чек каждой группы на число заказов в ней, сложите результаты и разделите на общее число заказов. Для точного расчёта нужны исходные суммы или средние до округления.

(n₁ · x₁ + n₂ · x₂) / (n₁ + n₂)  и  (x₁ + x₂) / 2x₁ и x₂ — средние чеки двух групп, n₁ и n₂ — число заказов в них. Слева каждый заказ получает одинаковый вес, справа одинаковый вес получают группы. Для двух непустых групп результаты совпадают, если группы одного размера или их средние равны.

В интерактиве собраны оплаченные заказы покупателей из четырёх стран. В каждой стране есть две группы — заказы с промокодом и без него. Заказ относится ко второй группе, если в поле промокода стоит NULL или пустая строка.

На шкале показаны суммы заказов, а точка опоры весов обозначает результат выбранного расчёта. В Беларуси заказов без промокода примерно впятеро больше, чем с промокодом, но средние чеки групп близки. В Казахстане у четырёх заказов с промокодом средний чек примерно на 1 854 ₽ выше, чем у остальных восемнадцати. Если дать обеим группам одинаковый вес, средний чек окажется завышен примерно на 590 ₽, или на 10%.

Тот же эффект виден при сравнении стран. Средний чек по всем 184 оплаченным заказам с известной страной покупателя равен 4 671,20 ₽. Простое среднее четырёх средних чеков по странам — 4 808,70 ₽. В следующем примере ROLLUP вычислит итог непосредственно по заказам.

05Промежуточные и общие итоги

GROUPING SETS задаёт несколько вариантов группировки в одном запросе. Например, GROUP BY GROUPING SETS ((channel), (brand), ()) выведет показатели по каналам, по брендам и по всем заказам. Пустые скобки означают группировку без разделения по столбцам9.

ROLLUP добавляет итоги по уровням. Запись ROLLUP(channel, brand) соответствует наборам (channel, brand), (channel) и (). В результате будут показатели для каждой пары «канал, бренд», итог по каждому каналу и общий итог9. Для всех оплаченных заказов средний чек равен 4 677,33 ₽. Если усреднить три средних чека каналов, получится 4 673,59 ₽.

В общей итоговой строке значение channel обозначено как NULL. Функция GROUPING(channel) вернёт 1, если channel не входил в набор группировки, и 0, если группировка велась по этому столбцу1. Так можно подписать общий итог и отличить его от группы заказов с неизвестным каналом.

06Три проверки для отчёта

Что означает каждый столбец после GROUP BY? В запросе SELECT brand, channel, COUNT(*) … GROUP BY brand для одного бренда может встретиться несколько каналов. PostgreSQL и DuckDB отклонят такой запрос3. SQLite вернёт значение channel из одной строки группы. Если в запросе есть ровно один встроенный MIN или MAX, SQLite выбирает строку с этим экстремумом. При совпадении экстремальных значений выбор строки остаётся неопределённым10. Для отчёта по каналам и брендам включите оба столбца в GROUP BY.

Какие заказы входят в знаменатель? Для 195 оплаченных заказов сумма 104 известных оценок равна 419. Средняя выставленная оценка, AVG(rating), равна 4,03. Если присвоить всем пропускам ноль, получится 2,15 балла на оплаченный заказ. Для такого правила подойдёт AVG(COALESCE(rating, 0)). В группе из 36 отменённых заказов все оценки пропущены. Здесь AVG(rating) вернёт NULL, а замена пропусков нулями даст 0.

Сохраняется ли дробная часть при делении? Результат зависит от диалекта SQL и типов операндов. В учебной базе amount имеет тип INTEGER. В PostgreSQL и SQLite выражение SUM(amount) / COUNT(*) для этих данных выполнит целочисленное деление: 912 080 / 195 даст 4 67711. В DuckDB оператор / сохраняет дробную часть, для целочисленного деления есть //12. Для среднего чека удобно взять AVG(amount). В расчёте процента отмен множитель 100.0 до деления сохранит дробную часть во всех трёх СУБД.

07Когда важен порядок событий

Группировка заказов по статусу покажет, сколько заказов оплачено или отменено. Для воронки понадобится история событий. Чтобы посчитать, какая доля посетителей дошла от просмотра до оплаты, для каждого посетителя проверяют время и порядок шагов, включая добавление в корзину.
